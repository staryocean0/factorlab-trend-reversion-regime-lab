## 1. 产品定位：这是状态识别组件，不是交易策略

本仓未来的核心交付是一个可被多个策略调用的**趋势状态识别组件（Layer 2 component）**。它回答的是：

> 在指定证券、指定 `as_of`、指定 K 线级别/配置下，当前价格序列属于什么趋势状态，趋势强度是多少，这个状态在什么时间边界内有效？

它**不**直接回答：买还是卖、持仓多少、何时下单、Layer 4 应执行什么动作。

因此，上层策略可以按自己的持仓周期和交易逻辑使用同一个组件。例如：某策略在 `SIDEWAYS` 使用均值回归模块，在 `UP` 使用趋势模块，在 `DOWN` 降低风险；另一个策略完全可以做不同映射。**状态到交易动作的映射属于策略层，不属于本组件。**

这也是与现有风险识别工具一致的架构方向：参考 `staryocean0/factorlab-star50-filter-lab` 已形成的只读 consumer / as-of 查询 / schema 与可用性边界，学习其“可调用组件合同”；但本组件只处理趋势状态及强度，不复制风险工具更复杂的风险持续时间、概率曲线等维度。

## 2. 非目标（Non-goals）

下列内容不是本组件职责：

- 输出 `BUY/SELL`、目标仓位、订单；
- 把 `UP` 自动解释成买点、把 `DOWN` 自动解释成卖点；
- 直接消费 Layer 4 或替代完整策略；
- 把多个 K 线级别强行合成为唯一“总趋势”；
- 因某次回测效果好而为单一策略私有化一套分类代码；
- 在证据不足时把研究分桶写成生产语义。

## 3. 为什么必须参数化

不存在脱离时间尺度的唯一趋势状态。同一时刻完全可能同时满足：

- `1m = DOWN`
- `5m = SIDEWAYS`
- `15m = UP`
- `60m = UP`

这不是冲突，而是不同观察尺度下的正常结果。

因此策略调用组件时必须绑定配置。V1 设计优先暴露两个消费维度：

1. **K 线级别 / `bar_interval`**：例如候选 `1m / 5m / 15m / 60m`；
2. **强度口径 / `strength_profile`**：定义横盘阈值、极端强度阈值及其版本。

回看窗口、斜率估计方法、归一化方式等低层参数可以存在，但原则上应被封装进有版本的 profile，避免每个策略随意拼一套算法导致组件失去统一语义。

长周期策略可以选择长周期 profile；短周期策略可以选择短周期 profile。**策略选择配置，组件保持同一套接口。**

## 4. 目标调用模型

以下只是合同方向，正式字段在路线图 M1 冻结，当前不把示意当成已经实现的 API：

```text
query_regime(
    symbol,
    as_of,
    bar_interval | profile,
) -> RegimeSnapshot
```

`RegimeSnapshot` 至少应能表达：

- `symbol`
- `as_of / decision_time`
- `bar_interval / profile / model_version`
- 离散 `state`
- 原始斜率或等价趋势度量
- 可跨配置解释的 `strength` / normalized strength（若经验证可定义）
- 实际采用的阈值版本
- `published_at / valid_until` 或等价时间边界
- `availability / reason`
- schema/version

目标行为参考风险识别 consumer 的关键约束：**只读、as-of、缺失/过期显式返回、不可悄悄回退到更老状态、调用者不能通过接口重写历史。**

## 5. 当前三桶基线

现有直觉基线是按趋势斜率 `s` 与横盘阈值 `T1 > 0` 分三类：

- `DOWN`：`s < -T1`
- `SIDEWAYS`：`-T1 <= s <= T1`
- `UP`：`s > T1`

三桶首先承担的是**状态描述**，不是收益预测。正式实现前还必须冻结斜率定义、回看窗口、归一化方式、K 线完成规则、阈值尺度以及 causality/as-of 约束。

三桶是后续研究的基线。五桶若没有稳定增量，组件应允许继续保留三桶，而不是为了“更细”而强行升级。

## 6. 五桶候选：把“极端趋势”单独作为研究对象

用户提出一个重要待验证假设：超过普通趋势阈值以后，**斜率越极端未必代表越值得顺势进入；极端斜率可能更接近趋势耗竭阶段，因此后续持续性反而下降。**

为检验这个猜想，候选五桶设第二阈值 `T2 > T1`：

- `STRONG_DOWN`：`s < -T2`
- `DOWN`：`-T2 <= s < -T1`
- `SIDEWAYS`：`-T1 <= s <= T1`
- `UP`：`T1 < s <= T2`
- `STRONG_UP`：`s > T2`

### H1：极端斜率耗竭假设

与普通 `UP/DOWN` 相比，`STRONG_UP/STRONG_DOWN` 可能表现出：

- 更短的状态持续时间；
- 更低的同方向延续概率；
- 更高的衰减、横盘或方向反转概率；
- 对 forward horizon 更敏感的非单调关系。

**H1 当前没有被视为事实。** 更不能把 `STRONG_UP = SELL` 或 `STRONG_DOWN = BUY/SELL` 写进组件。即使统计上验证“极端状态更容易耗竭”，具体如何交易仍由调用策略决定。

五桶的真正问题不是“能不能切五份”，而是：**把极端桶单独分出后，是否得到跨样本、跨阈值、跨 K 线级别仍稳定的不同状态语义。**

## 7. 三桶、五桶与连续强度并非三选一的先验答案

未来允许三种正式架构：

1. **三桶 + 连续强度**：离散状态保持稳定，强度单独输出；
2. **正式五桶**：只有在极端桶确有稳定不同持续性/转移特征时采用；
3. **三桶主状态 + 五桶研究扩展**：五桶只供诊断，不给稳定接口语义。

最终选择必须由实证决定，而不是由分桶形式的美观决定。

## 8. 与风险识别组件、策略层的关系

两个组件应并列服务策略，而不是互相吞并：

```text
市场数据
  ├─> 趋势状态识别组件：方向 / 横盘 / 强度 / 时间尺度
  └─> 风险识别组件：风险状态 / 风险强度 / 持续性等
              ↓
        策略层按自身周期调用并组合
              ↓
        交易决策 / 仓位 / Layer 4
```

趋势组件不需要知道某个策略最终是趋势跟随、均值回归还是择时；风险组件也不应替策略做交易决定。策略匹配问题通过**参数化调用与 profile**解决，而不是把组件改造成一个“万能策略”。

## 10. 路线图与执行纪律

完整路线图见 [ROADMAP.md](ROADMAP.md)。顺序固定为：

`M0 定位/路线图 → M1 接口合同 → M2 三桶基线 → M3 多周期 → M4 五桶实验协议 → M5 实证 → M6 架构裁决 → M7 Consumer API → M8 策略集成 → M9 发布治理`

核心纪律：

- **一次会话只推进当前里程碑。**
- 当前 Gate 没过，不自动跳到下一阶段。
- 先冻结问题和评价口径，再运行会影响结论的实验。
- 负结果是允许结果；五桶验证失败就保留三桶/连续强度。
- 不为了某个策略的回测收益修改状态定义后再反过来声称组件“客观识别”了趋势。

本轮只完成 M0 文档定位，不启动 M1 之后的代码或实证工作。
